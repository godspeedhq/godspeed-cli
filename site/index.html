Build for GodspeedOS without learning its insides.

godspeed creates, builds, packages, signs and publishes software for GodspeedOS - for all four of its architectures at once - using only the OS's public contracts. You never touch the kernel, raw IPC or the supervisor.

$ godspeed new service hello
$ cd hello
$ godspeed build --all      # x86_64, aarch64, armv7, riscv64
$ godspeed publish          # signed, uploaded, installable as you/hello

What you can build today

Godspeed has five kinds of project. The CLI makes a template only for a kind the OS can actually run, and says plainly why the others must wait - it never generates a project that cannot do what its kind promises.

Service works

A managed program with a lifecycle and a declared request for authority. Every runnable program on Godspeed is a service today.

godspeed new service clock

Library works

Reusable no_std Rust for other Godspeed projects. Its tests run on your workstation.

godspeed new library parser

Utility waits on the OS

A program that does one job and ends. GodspeedOS has no terminating task yet.

App waits on the OS

A user-facing program. There are no public application interfaces yet.

Driver waits on the OS

A userspace driver. A driver from outside the OS tree has no way yet to be granted a device.

Ask for one that must wait and you get the reason, where the OS tracks it, and what to do instead:

$ godspeed new utility status
Cannot create a utility project
Stage: validation
Reason:
  A utility is a program that does one job and ends. GodspeedOS has no terminating task yet: every
  program is a service that never returns, and there is no way for a program to end itself.
Expected:
  tracked in GodspeedOS docs/stdlib-design.md, section 1 (options A and B)
Next:
  Create a `service` instead - every runnable program on Godspeed is a service today.

The examples show real services and libraries, each built for every architecture in CI.

Get started

  1. Install Rust and the CLI

    You need Rust and nothing else. No release of the CLI has been cut yet, so build it with Cargo:

    $ cargo install --git https://github.com/godspeedhq/godspeed-cli --branch feat/cli-foundation --locked godspeed-cli

    Once the first release is out, a one-line installer will fetch a prebuilt binary for Linux, macOS or Windows (x86_64 or Arm64) and check it against the release's checksums. Running it again updates; the CLI tells you, at most once a day, when there is a newer release.

  2. Point it at a GodspeedOS release

    The CLI builds against an OS checkout - its standard library release, its pinned compiler and its contract schema. It reads that checkout and never writes to it.

    $ git clone --branch v0.28.0 https://github.com/godspeedhq/godspeed-os
$ export GODSPEED_OS=$PWD/godspeed-os      # Windows: $env:GODSPEED_OS = "$PWD\godspeed-os"
$ godspeed doctor

    doctor checks the toolchain, all four targets and QEMU, and prints the command that fixes anything missing. (On Windows, run git config --global core.longpaths true first: the OS repository has some long file names.)

  3. Create and build

    $ godspeed new service hello
Created service hello in hello (GodspeedOS v0.28.0)
$ cd hello
$ godspeed check
service hello is valid against GodspeedOS v0.28.0.
$ godspeed build
Validating project...
Fetching dependencies...
Building hello for x86_64 (x86_64-unknown-none)...
Built x86_64 target/x86_64-unknown-none/release/hello
These are service binaries, not an OS image; nothing was installed or run.

    It is an ordinary Rust project, so cargo fmt and cargo clippy work in it as usual, with the compiler the OS pins.

  4. Package it, and look before anything leaves your machine

    $ godspeed package
Verified alice/hello 0.1.0 (service), built against GodspeedOS 0.28.0
  contract.toml              sha256:762be027...
                 requests: log_write
  x86_64.elf        18952 B  sha256:2f3fa20d...
  aarch64.elf       78760 B  sha256:d0896436...
  armv7.elf         16644 B  sha256:b1443f11...
  riscv64.elf       30968 B  sha256:ba2ac5b2...
What the contract requests is not granted by installing it.

  5. Publish

    Make a signing key and a token once, then godspeed publish. Publishing walks through it.

What works, and what waits

The first half of the workflow works end to end, against the live registry. The second half needs things only the OS can provide, and the CLI will not paper over them.

StepStatus
Create, check, build for every architectureworks
Test a libraryworks
Package, sign, verifyworks
Publish, and fetch with every signature checkedworks
Test a servicewaits on the OS a service runs only on a Godspeed machine
godspeed runwaits on the OS no public way to run a service built outside the OS tree
godspeed install on a Godspeed machinewaits on the OS the OS starts only the programs it was built with

Can I use C, C++ or Go?

Not yet. A Godspeed program today is Rust, because the only public way to talk to GodspeedOS is its Rust standard library, gs. Nothing else about the CLI is tied to Rust: a package is a contract plus one ELF per architecture, and the format does not care what compiled them.

  • C and C++ need a C interface to gs - a header and a library - and a freestanding compiler for each architecture. That is a plausible addition, and it is the OS's to define. Once it exists, the CLI gains a second way to build, and packaging and publishing stay exactly as they are.
  • Go needs much more: its runtime - scheduler, garbage collector, system interface - ported to GodspeedOS, which has no POSIX layer and no heap for services.

Until the OS defines one of those, the CLI does not offer a C, C++ or Go template: it would be one that cannot do what it promises.

How it behaves

Requests, never grants

A contract asks for authority. What a program is actually given is the operating system's decision, never the package's or the CLI's.

Every refusal is actionable

What failed, why, what was expected, and what to do next - with a distinct exit code for scripts and CI.

No invented certainty

If a publish times out, the CLI reads the registry and reports what it finds. "Outcome unknown" is an answer, not a failure.

No cloud lock-in

The CLI speaks the registry protocol, never a storage provider's API. A package can be hosted by any registry or mirror.
