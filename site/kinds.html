What you can make

GodspeedOS runs four kinds of program, and godspeed new makes every one, plus libraries for them to share. Each kind is a different answer to one question: whose life does the program live? Pick the kind, and the template is the smallest program of it that works.

Service

The system's. Started at boot, restarted if it dies.

Utility

Its own. Runs when typed, ends with a status, pipes.

App

The operator's. Has the screen and keyboard while it runs.

Driver

Its device's. Given one device, by what the bus says it is.

Library

Nobody's. Built into what uses it, tested on your workstation.

What every kind shares

  1. Make it, and check it

    $ godspeed new <kind> <name> --publisher <you>
$ cd <name>
$ godspeed check            # the project, its toolchain, and its contract against the OS's schema
$ godspeed build --all      # one ELF for each of x86_64, aarch64, armv7, riscv64

    Every template is written on the public standard library, gs, and nothing below it. CI makes, checks and builds every kind for all four architectures against the GodspeedOS release it names, so a template that does not build is a bug in this CLI.

  2. Package and publish it

    $ godspeed package          # every file, with its size and SHA-256, before anything leaves
$ godspeed publish          # signed, uploaded, installable as you/<name>

    No network on the machine? godspeed package --local writes one .gsp file, signed with your key, that a machine installs once its operator trusts that key. Publishing has the one-time setup.

  3. Install it, on a Godspeed machine

    gsh> godspeed install <you>/<name>

    Installing asks the operator for what the contract requests, by name, and grants nothing else. The contract asks; the machine decides.

Service works

A program the system keeps running: the supervisor starts it at every boot and restarts it if it dies. The shape of every server, logger and background job.

$ godspeed new service clock
#[no_mangle]
pub extern "C" fn service_main(ctx: ServiceContext) -> ! {
    ctx.log("clock: started");
    gs::ipc::park(&ctx)
}
  • Given: what its contract requests and the operator approves - log_write in the template, and send peers by name.
  • Upgraded live: put handover = true under its contract's [capabilities], and godspeed upgrade hands the old version's state to the new one with no restart.
  • Needs another package? Name it in godspeed.toml, and the machine installs and starts it first: 
    [requires]
"alice/notes-store" = "^1.2.0"
    A requirement grants nothing: the contract still names every peer it talks to.

Utility works

A program that does one job and ends, like a built-in command: typed at gsh> by its name, given its arguments, its output shown or piped, its status said.

$ godspeed new utility greet
let mut buf = [0u8; gs::program::ARGS_MAX];
let args = gs::program::args(&ctx, &mut buf);
let mut out = gs::program::Output::new(&ctx);
let _ = writeln!(out, "hello, {}", if args.is_empty() { "world" } else { args });
out.finish(0)
gsh> greet Ada
hello, Ada
gsh> greet Ada | count
1 line, 2 words, 11 bytes
  • Given: its arguments and an output stream, through gs::program. It ends with finish(status) or gs::program::exit, and is never restarted for it.

App works

A program the operator uses: it has the screen and the keyboard while it runs, and gives them back when it ends - even if it crashes.

$ godspeed new app notes
let app = gs::app::App::open(&ctx);
app.println("This screen is notes' until a key is pressed.");
let _key = app.wait_key();
app.close(0)
  • Given: the console, through gs::app - asked of the operator by name at godspeed install, because a program that holds the keyboard reads what is typed.
  • An app cannot start a pipe: it has the screen, not a stream. Windows, and graphics beyond the console's grid, are not offered.

Driver works

A program that drives one device. Its contract names the device by what the PCI bus says it is - never an address - and the machine finds which device that is.

$ godspeed new driver sensor
[capabilities]
hw_pci_class = "00ff00"   # QEMU's teaching device, `edu`
hw_pci_bar   = 0          # its registers are in BAR 0
let Some(regs) = gs::driver::registers(&ctx) else {
    ctx.log("sensor: no device was granted - nothing to drive");
    gs::ipc::park(&ctx)
};
regs.write32(FACTORIAL, 5);
// A bounded wait, by time: one that never ends is said, not waited on forever.
if wait::until(&ctx, Budget::ms(10), || regs.read32(STATUS) & COMPUTING == 0).is_err() {
    ctx.log("sensor: the device is not answering");
    gs::ipc::park(&ctx)
}
  • Given: its device's register window, and nothing else - no DMA arena and no interrupt yet. It is the same library the OS's own drivers are written on, gs::driver: registers for the window, wait for a bounded wait on the device, and delay for a hold nothing can report the end of.
  • A class a GodspeedOS driver already handles is refused at install, so a package never takes a device from the OS.
  • The template drives QEMU's edu (-device edu): installed, it logs device id 0x010000ed, alive true, 5! = 120.
  • Needs GodspeedOS v0.30.0 or later, the first release with gs::driver::registers.

Library works

Reusable no_std Rust for the other kinds. Never installed: it is built into what uses it, so it requires no packages. Its tests run on your workstation.

$ godspeed new library parser
$ godspeed test
